## 1. Emergency Services — orphaned-request fix

**Problem:** When a user requested an emergency service (snake catcher, private ambulance, mortuary van) in an area with no available providers, the request was silently persisted as `pending` in MongoDB. Subsequent attempts hit the active-request guard and returned 409 `REQUEST_EXISTS`. The user's history showed an orphan ticket they couldn't dismiss.

**Root cause:** The flow was *create-then-search* — `createEmergencyRequest` saved the document before `getNearbyProviders` ran. When the search returned empty, neither side cleaned up the now-orphaned doc.

### Backend — `noefi/fixhomi-backend/controllers/emergencyServicesController.js`

- **`getNearbyProviders` (~line 437):** When zero providers match after exhausting search radius, atomically transition the request to `cancelled` (gated on `status: 'pending'` + unassigned to avoid racing with a concurrent assignment). Response includes `requestCancelled: true`.
- **`createEmergencyRequest` (~line 185):** Sweep stale `pending` orphans for this user+service older than 10 min with no provider assigned. Marks them `cancelled` with reason `stale_pending_swept`. Guarantees no permanent lock-out even when a client misses cleanup.

### Frontend — `renfi/renfi/src/screens/EmergencyServicesScreen.jsx`

- **`handleCreateRequest` no-providers branch (~line 798):** Calls `cancelEmergencyRequest` defensively (skipped when backend reports `requestCancelled: true`); clears `createdRequest` so retries start clean.
- **`handleCreateRequest` catch (~line 815):** Cancels the orphan if the create succeeded but providers call failed.
- **`handleRetryProviders` no-providers branch (~line 853):** Same cleanup pattern.
- **New unmount-cleanup `useEffect` (~line 729):** Uses refs to track latest `createdRequest`/`step`. If the screen unmounts (back gesture, navigation, app close) before reaching `step === 'providers'`, fires a best-effort cancel.

**Net:** Three layers of defence — server-side per-search auto-cancel, server-side stale sweeper, client-side cleanup.

## 2. Auth — duplicate-user / unified-ID safety on register retries

**Problem:** A retried `POST /register` (after a network drop swallowed the first response) could break the `mongoId === javaUserId` invariant. Java Auth's "reclaim unverified email" path deactivates the original user and mints a new userId. The Mongo doc still pointed to the stale userId, so future profile lookups by the new userId returned nothing — user has tokens but cannot load their profile.

**Verified safeguards already in place** (agent had over-flagged these as missing):
- Java `User` entity has DB-level UNIQUE on `email`, `phone_number`, and `apple_user_id` (`User.java:18-21, 31, 69`).
- Mongo `User` schema has UNIQUE on email (line 77) and sparse-unique on phone (line 348).
- `AuthService.register()` is `@Transactional` — constraint violation rolls back atomically.
- `apiClient.js:272-277` retries POST on transient network errors (this is the trigger for the bug, but with the fix below, retries are safe).

### Backend — `noefi/fixhomi-backend/controllers/authController.js`

- **User register (~line 314):** Inserted orphan-reconcile block before the duplicate-handling branch. If `existingUser.javaUserId` differs from the new Java response's `userId`, soft-delete the orphan (rename email to `migrated_<id>_<ts>@deleted.local`, set `isDeleted: true`, `deletedAt: now`), then fall through to the upsert path which creates a fresh doc with the correct unified `_id`.
- **Provider register (~line 1170):** Replaced the broken `needsUpdate` block. The previous code overwrote `javaUserId` to the new value while leaving `_id` stale — this *actively broke* the unified-ID invariant. New code soft-deletes the orphan and falls through to a clean upsert. Backfill path now only fires for the legitimate cases (missing javaUserId or isDeleted reactivation).

### Backend — `noefi/fixhomi-backend/controllers/googleAuthController.js`

- **Google provider sync (~line 351):** Same orphan-reconcile pattern as the existing (already-correct) Google user sync at line 86. Detects mismatch, soft-deletes orphan, falls through to fresh upsert.

**Apple OAuth:** No fix needed. Apple flow keys off Java's unique-indexed `apple_user_id`, doesn't traverse the `email` reclaim path, and has no Node-side OAuth controller that creates Mongo docs.

**Net:** The `mongoId === javaUserId` invariant now holds across all auth paths even under retry / response-loss scenarios.
